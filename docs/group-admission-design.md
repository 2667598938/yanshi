# 学习小组邀请与审批：独立设计稿

本文件是待确认、未接线的设计，不代表新增表或接口已存在。本次代码清理不改变任何enroll调用点、现有成员或VIP兑换行为。当前有效规则仍见[当前规则](design-2026-10-25/PRD-当前规则.md)。

## 权限与业务边界

- 注册只建立账号，加入公开/私密房间只取得房间准入，不授予小组学习数据读取权限。
- 学习小组邀请与VIP邀请码使用独立实体、字段、路由及文案。获取VIP或获得AI/资料等功能授权，不应成为新流程中的入组凭据。
- 已在小组的成员仍默认按现有共享/隐私规则只读互看；待审批成员不能查询学习记录、题图、在线状态或位置。
- 由明确的小组管理角色邀请和审批；平台账号管理员的身份本身不授予学习隐私旁路。现有管理员建号即作为受邀成员的行为保留。

## 建议交互

1. 小组管理者生成有期限、可撤销、可指定账号的独立邀请链接/码，原始令牌只在生成时展示。
2. 已登录账号凭邀请提交入组申请。建议默认需要管理者批准；“持有效邀请直接加入”是否开放需明确决定，不暗中采用。
3. 管理者查看待审申请，只查看申请所需的账号身份和申请理由；批准/驳回填写结果，驳回需要原因。
4. 批准时同事务校验邀请有效性、申请版本、账号状态和是否已入组，再写成员关系、申请结果、通知和审计。后台调用现有enroll服务，不复制第二套成员写入逻辑。
5. 重复提交返回同一待审申请；重复批准返回已处理结果。并发审批不能重复消耗邀请名额、生成重复成员或发送重复通知。
6. 用户可以撤回待审申请；过期或撤销邀请不能被继续使用。拒绝和撤回不会授予任何学习访问权限。

## 目标数据与接口（尚未实现）

- 独立小组邀请：group_id、令牌摘要、指定接收账号（可选）、到期/撤销时间、使用次数与上限、创建者。不得复用VIP invites表。
- 入组申请：group_id、user_id、邀请引用、pending/approved/rejected/cancelled状态、revision、理由、处理人/原因/时间。同账号同组最多一条待审申请。
- 小组管理角色及授权事实需明确建模；现有成员表不能仅靠前端按钮推断管理资格。
- 用户接口：提交、查看本人申请、撤回；管理接口：生成/撤销邀请、待审队列、批准/驳回。每个接口后端鉴权，申请列表不混入学习数据。
- 名额按小组策略单独判断，不把平台账号上限或单房容量当成小组名额。

## 迁移与验收要求

- 保留所有既有成员，禁止因为本次解耦就自动移出已合法加入的人。
- 切换注册中的VIP码兼容路径前，需要明确新的入组凭据和用户提示，再调整调用点；本设计稿不执行切换。
- 验证普通注册不入组、房间成员不等于组员、VIP兑换不入组、新邀请审批、并发重复处理、撤回/过期/撤销和非组员直接访问拒绝。
- 复验批准后默认共享、隐私开启后隐藏、移出组后数据和图片立即失权；AI会话/Key、资料私人备注始终不共享。
